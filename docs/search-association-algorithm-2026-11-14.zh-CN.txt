DFCN 搜索关联算法方案
版本：2.0
日期：2026-11-14
状态：统一搜索引擎、原生描述器、领域接入及运行数据已实现。原生字段不可用时保留 Unknown；游戏内最终显示效果尚未实际观察。

一、目标与统一决策

搜索以“原生候选对象的结构化含义”为中心。英文原名、中文译名、俗称、拼音、类别、材料、用途和任务产物分别进入对应字段，再由查询中的关系把这些字段连接起来。

最终匹配定义为：
  当前页面原生候选集合
  ∩ 至少一个完整查询解释所要求的对象集合
  ∩ 该解释的全部明确限定条件。

同一解释内部为 AND；不同合法解释之间为 OR；否定只作用于明确的被否定字段。模型相似度只参与不确定词义的召回与排序，不能覆盖已确认的对象身份、材料、状态或否定条件。

确定采用以下结构：
  原生候选描述器 → 有来源的概念与关系目录 → 查询解析图
  → 词面／拼音／类别／用途／模型多通道召回 → 字段约束匹配
  → 分层相关度 → 返回原生候选身份及匹配结果。

运行时使用本地数据和已有离线模型，不查询网络。Wiki 提供编写关系规则时的资料；游戏二进制和当前世界实际加载的定义决定事实与可用候选。

搜索只决定已有候选是否与查询相关，不新增任务、不选择材料、不下达工单，也不把“符合搜索”解释为“当前材料足够或能够执行”。原生禁用原因、候选分组、数量、勾选状态、选择身份和建造可用性继续由各页面原有逻辑决定。

二、本次确认的原生事实

2.1 当前研究对象

当前配置的 Steam 游戏映像为 Windows x64 53.17：
  D:/program/steam/steamapps/common/Dwarf Fortress/Dwarf Fortress.exe
  SHA-256：3436f0553d6fa17b25716f8b1f034b52e3d9dc30be7f3ddac67cd0ff731d7b16

使用本机 Ghidra 12.1.4 对同一磁盘映像进行离线反编译。未读取游戏进程、游戏加载日志或桌面；原有 Ghidra 工程以 -readOnly 打开，分析修改未写回工程。地址由该映像已有的静态地址映射定位，并按 PE 异常展开链恢复函数的多个代码区间。

本次实际导出的六个函数及其完整区间见：
  data/extracted/search-association-2026-11-14/coordinates.tsv

角色                         当前映像入口 RVA
工作订单候选过滤             0x3cc280
工坊候选过滤                 0x1a9da0
储物堆设置过滤               0x3c54e0
工作任务标题构造             0xd1afa0
物品需求名称构造             0xa9c6b0

这些角色名是研究命名，不是游戏自带调试符号。工作订单过滤等函数有 chained unwind 区间，不能把第一段的结束地址当作整个函数结束。

2.2 搜索与身份分离

工作订单过滤函数读取当前分类 +0x40、查询字符串 +0x50，遍历该分类的任务记录，对记录 +0x70 的折叠名称做字符串查找，把结果写入 +0x90。清空查询恢复当前分类内记录的显示。候选填充函数先调用任务标题构造器写入记录 +0x50，再把其副本 +0x70 折叠用于搜索。

结论：原生任务参数和原始标题在筛选时仍然存在。新引擎从这些字段建立任务描述器，不从被折叠的字符串猜回任务身份。搜索范围仍是原生分类允许的记录。

证据：work_order_filter.c、work_order_population.c；对应原始指令在同名 .asm 中。

储物堆过滤函数使用查询 +0x18，遍历 +0xd8 所指的候选数组，对候选 +0x20 的搜索字符串查找，写候选可见位 +0x48，并维护界面匹配计数 +0xf4。

结论：搜索匹配结果不能替代储物堆的开关指针、列类型或原生计数维护。类别、材料、品质等列的含义必须通过页面上下文传入。

证据：stockpile_filter.c；现有接入为 src/native_stockpile_search_hooks.inc。

工坊过滤函数先对候选名称查找，再通过候选虚方法区分结果分组；部分分组另有内部顺序。因此匹配器不自行重建候选、不合并不同菜单记录，也不把整个结果容器直接按一个分数重排。

证据：workshop_filter.c，尤其 native find 后的 virtual +0x50 分支。

2.3 名称并不等于类型

当前任务标题构造器的 0x49 分支根据材料产生 box、coffer 或 chest；0x46 分支产生 chair 或 throne；0x4e 分支构造材料前缀加 cabinet。需求名称构造器对 BOX 也有材料相关名称分支。

相同对象类别可以有多个英文名称，不能把每个名称各建成互斥类型。反过来，名称里含有 weapon 的 weapon rack 并不是 WEAPON。

证据：job_caption.c 的对应 switch 分支及 decompiled-literals.tsv 中的磁盘字面量；df.d_basics.xml 的 item_type；df.job.xml 的任务与产物类型关系。

反编译限制：job_caption 在 0x140d1fc4c 留有 Ghidra pcode 解码警告；本方案引用已展开的上述分支，不把整份 C 当作已完整恢复的所有任务规则。Ghidra .asm 为其已识别指令列表，不能声称包含该大函数的所有 switch 分支。未被自动命名的 UNK 字符串通过 decompiled-literals.tsv 对照磁盘内容。53.16 的旧反编译资料只作补充，不把旧 RVA 直接用于 53.17。

2.4 RAW 提供名称之外的关联

当前安装的 item_tool.txt 中：书架是 ITEM_TOOL_BOOKCASE，带 TOOL_USE:BOOKCASE、FURNITURE 和容量；展示柜、展示台使用 TOOL_USE:DISPLAY_OBJECT；大罐使用 FOOD_STORAGE。df-structures 的 itemdef_toolst 保存 tool_use、flags、adjective、container_capacity 等字段。

因此书架、展示柜不是新的原生 item_type；它们是 TOOL 的具体定义，另有用途与家具属性。翻译语法中的 items::bookcase、items::displaycase 是名称解析空间，不能直接充当原生类型编号。

当前 reaction_other.txt 明确区分 REAGENT、PRODUCT、PRODUCT_TO_CONTAINER、GET_MATERIAL_FROM_REAGENT 等。制革、制皂、陶器等任务的投入物、产物及材料传递关系分别记录，不能把整段任务说明里的所有名词都算成任务产物。

三、Wiki 资料对关系建模的约束

资料在 2026-11-14 查阅；Wiki 主命名空间有些页面标注 53.16 或更早，实际世界定义和当前二进制优先。

1. Furniture 明确区分储物堆、锻造菜单和放置建筑的家具口径；同类型家具还可能因材料而使用不同名称。因此建立多个有作用域的类别，不能把“家具”压成全局唯一原生集合。
   https://dwarffortresswiki.org/Furniture

2. Storage 区分橱柜、箱子、桶、罐、袋等储物用途；橱柜与箱子在卧室内储存的对象不同。因此“容器”“装衣物”“用于卧室”是不同关系，“能存放”也不等于“当前装着”。
   https://dwarffortresswiki.org/index.php/Storage

3. Tool token 将 TOOL_USE、FURNITURE、CONTAINER_CAPACITY 分开定义。因此用途、菜单／储存属性和容量分别建字段，不从一个属性推导全部其他属性。
   https://dwarffortresswiki.org/Tool_token

4. Armor token 区分 ARMORLEVEL、LAYER 和有条件的 METAL_ARMOR_LEVELS。当前页面还说明旧版本的等级叫法与当前解释不同。因此防具分类是带版本和材料条件的谓词，不把整个 ARMOR 原生类型等同于防具。
   https://dwarffortresswiki.org/index.php/Armor_token

5. Material definition token 区分 STATE_NAME、STATE_ADJ、材料状态、材料属性和模板继承。因此“木材／木制”等属于同材料的名称形式，而不是通过英文或中文词尾任意删除得到的同义词。
   https://www.dwarffortresswiki.org/index.php/Material_definition_token

6. Reaction 区分输入、输出、保留容器、材料反应产物和条件。因此生产关系采用有方向、有角色、可带条件的边。
   https://dwarffortresswiki.org/index.php/Reaction

7. Work orders 将物品条件的类型、材料和形容属性分开；Stockpile 也有不同类别及属性列。因此上下文必须进入查询计划与缓存键。
   https://dwarffortresswiki.org/index.php/Work_order
   https://dwarffortresswiki.org/index.php/Stockpile

8. 现有 potion-multilingual-128M 为 256 维静态词向量模型。项目 pool() 累加 token 向量后归一化，不能可靠表达词序、否定和输入／输出角色。角色由解析器决定，向量负责相近词义。
   https://huggingface.co/minishlab/potion-multilingual-128M
   本地实现：src/search_semantic_model.h。

四、替换前实现的具体缺口

以下记录替换前的源码结构问题，作为本次实现的背景，不是新引擎现状、运行测量或游戏内结果。

4.1 身份以翻译结果构成
SearchItemTaxonomy 使用 noun.kind + 中文目标构成部分 concept key。相同译名可能合并不同原文定义；翻译改动还会改变身份。kind 又来自 items:: 命名空间，和原生枚举不严格相同。

4.2 RAW 丢失定义标识与有效范围
raw_nouns() 保留 kind、单复数和少数装备标记，没有保留完整 ITEM_* ID、TOOL_USE、FURNITURE、材料许可与反应关系。它扫描安装目录，而不是以当前世界已加载定义为事实集合。构造器又以英文 singular 连接现有概念，存在同名、不同类型或不同 mod 定义混接的风险。

4.3 所有关系挤进 parents
当前 group/kinds 适合简单类别，不能表达 produces、requires、stores、made_of、has_state、part_of，更不能表达关系的条件和页面作用域。

4.4 限定词没有字段角色
目前主要解析末尾对象，把前缀保存成 qualifier，再对整个候选标题递归匹配。它不能严格区分“铁制箱子”与“装铁的箱子”，也不能直接表达“用木桶装酒”的容器和内容角色。

4.5 确定性粒度过粗
Query.certain 是整个查询的单一布尔值；finish_query 在出现 facet 时删除非 facet 解释。一个词可能同时是类别词、专名或模组子类型，不能用一次全局选择消灭其他完整解释。

4.6 词素与形态推断缺少义项约束
词素按英文拼写共用中文 forms；对齐推得的词素可继续进入确定匹配。英语复数目前主要处理 -s/-es/-ies。中文“子／儿”规则只能附着在已识别词上，不能自己证明“柜”和“橱柜”同义，也不能无限推广到所有末字相同的词。

4.7 向量和缓存仍以标题为主
每个候选可能建立标题及多个局部片段的 ANN 索引，许多候选共享的类型与材料语义被重复保存。ANN 96／512 的访问上限属于近似搜索；原生遍历全部候选不等于向量邻居无遗漏。预算耗尽和确定不匹配不能缓存为同一种状态。

4.8 原生英文命中的处理不统一
物品与工坊接入在部分路径先做类型决策；储物堆、建造材料等路径可能在原生 substring 命中后直接返回。新引擎统一处理匹配入口，避免相同查询因语言或页面走不同约束。

上一轮增加的“柜子／衣柜／衣橱”关联保留为一个词义的确定词汇记录。它解决已知称呼的映射，但不代表已经具备用途、状态、输入输出或泛类别推理。

五、身份、描述器与事实模型

5.1 稳定身份

概念身份不使用中文译名，也不使用当前屏幕行号。

  NativeTypeId       = 游戏 item_type 枚举
  DefinitionId       = 对象域 + 生效包身份 + RAW ID
  MaterialId         = 原生 material type/index + 来源域
  RecipeId           = 原生 job type 或 reaction ID + 固定参数
  EntityId           = 世界代次 + 原生对象 ID
  LexicalSenseId     = 语言 + 词义 ID + 领域
  CandidateId        = 页面所有者 + 列表代次 + 原生记录身份

同一 RAW ID 在磁盘安装多个版本时，只由当前世界实际生效定义生成事实。磁盘可提供词汇资料，不能据此将未加载定义宣布为当前可用类型。世界生成的材料、乐器和子类型采用运行时真实 ID 与原生名称。

翻译命名空间另存 SurfaceGrammarId，通过明确映射指向上述身份。例如：
  items::cabinet  → item_type:CABINET
  items::bookcase → item_type:TOOL + DefinitionId:ITEM_TOOL_BOOKCASE
  items::pot     → item_type:TOOL + 对应生效定义

5.2 候选种类

CandidateKind 固定区分：
  ItemInstance      真实物品
  ItemGroup         库存聚合项
  ItemDefinition    类型／子类型选项
  JobTemplate       工坊或工单任务模板
  MaterialChoice    材料选项
  PropertyChoice    品质、状态、用途等属性选项
  MenuCategory      原生类别入口
  NamedEntity       单位、小队、地点、组织等
  TextRecord        历史、日志、对话等文本记录

相同“柜子”查询在 ItemInstance 页面找实际橱柜，在 JobTemplate 页面找产出橱柜的任务；不会把这两种候选当成同一数据结构。

5.3 SearchDescriptor

  candidate_id / candidate_kind / domain / native_ordinal
  native_type / definition_id / entity_id / custom_name_origin
  original_caption / display_caption / display_name / lexical_labels
  base_material / material_state / material_categories
  subtype_traits / equipment_slot / size_constraints
  quality / wear / ownership / status / contained_items
  purposes / contextual_categories / component_relations
  job_action / fixed_parameters / selectable_parameters
  inputs / outputs / preserved_tools / required_workshop
  fact_provenance / field_completeness / snapshot_generation

base_material 与 decoration_material、contained_item.material 分开；quality 与 wear 分开；物品数量与制作批量分开；definition capability 与 instance state 分开。

ItemGroup 不能用一个成员满足“铁”、另一个成员满足“柜子”来证明整行命中。只要原生分组允许混合成员，就使用“存在同一个成员满足整个查询”的量词。组级计数仍由原生规则解释。

5.4 三值事实和条件事实

每个谓词返回 True、False、Unknown，并携带来源与适用范围。

  未读取内容列表 ≠ 空容器。
  未知材料 ≠ 任意材料。
  未显示禁用原因 ≠ 可执行。
  可选木材的任务 ≠ 已指定木材的任务。
  可储存酒 ≠ 当前装有酒。

明确硬条件只有 True 才算得到证明；False 排除该解释；Unknown 不冒充满足条件。普通文本回退可以保留独立的完整名称解释，但不能绕过用户显式写出的材料、状态、否定或字段条件。

六、词义目录与关系图

6.1 词汇与显示分离

Lexeme 记录：
  surface、language、sense_id、target_concept、domain、role、source、form_kind。

form_kind 区分：原生名称、当前译名、确认同义词、俗称、历史译名、材料名词／形容词、单复数、全拼、首字母、弱拼写变体。

“柜子、衣柜、衣橱、橱柜”在本游戏物品域指向 CABINET 的词义；界面仍显示现有译名。“柜类”建立单独的泛类别词义，可收录书柜、展示柜等。泛类别和 CABINET 不能通过同义词闭包被合并。

对一词多义保留多个 LexicalSenseId。例如“甲”不能全局固定为防具，“金”不能把所有含此字的专名改成黄金。“铁木”先保留已登记的完整植物／木材词义，不能直接拆成铁与木。

6.2 关系类型

关系                    方向与查询作用
ALIAS_OF                 词形 → 同一义项；义项内对称等价
IS_A                     子类 → 父类；查询父类召回子类
INSTANCE_OF              物品 → 定义／类型
HAS_MATERIAL             物品 → 基础材料
HAS_STATE                物品 → 当前状态
HAS_PROPERTY             定义或实例 → 已定义属性
HAS_CAPABILITY           定义／条件化实例 → 用途能力
STORES                   容器类别 → 允许储存的对象类别，带模式／场所／状态条件
CONTAINS                 当前容器实例 → 实际内容
PRODUCES                 任务 → 产物描述或产物约束
CONSUMES                 任务 → 消耗的投入物约束
REQUIRES_TOOL            任务 → 保留工具或容器
USES_WORKSHOP            任务 → 工坊类型
PLACED_AS                物品 → 放置后的建筑类型
COMPONENT_OF             零件 → 所属成品
DECORATED_WITH           物品 → 装饰材料／对象
MEMBER_OF_CATEGORY       对象 → 有页面作用域的类别
RELATED_TO               人工整理的弱关联；不参与默认确定匹配

每条关系包含 source、version_scope、domain_scope、conditions 和 evidence_kind。相似度产生的候选义项不写回关系图，不自动升级为 ALIAS_OF。

6.3 可传递范围

只有同一义项内部的别名等价、已确认 IS_A 的继承允许闭包。类别继承无环；发现循环时按等价类别组件处理或隔离冲突边，不让查询递归失控。

禁止“先找共同祖先，再枚举全部兄弟”：柜子属于家具，不意味着搜柜子要返回床和桌子。用途边、材料边、输入输出边不具备任意传递性。

允许的跨关系路径由查询意图指定：
  找物品：候选 INSTANCE_OF → 目标定义／类型 → IS_A*
  找某类产物的任务：候选 PRODUCES → 目标对象 → IS_A*
  找有某用途的物品：候选 HAS_CAPABILITY → 用途
  找制造用途物品的任务：候选 PRODUCES → 对象 HAS_CAPABILITY → 用途
  找消耗某物的任务：候选 CONSUMES → 投入物
  找容器内物品：候选 CONTAINS → 内容对象约束

IS_A* 是有限类别图内的继承闭包，不是沿所有边无限扩展。不同关系的逆向查询使用独立索引和明确语法，不默认双向化。

6.4 来源裁决

对象身份、当前状态、活动定义和固定任务参数以原生记录为准；名称对应以当前完整翻译语法及其明确绑定为准；词汇俗称以词义词表为准；用途关系由 RAW、已恢复的原生规则和带版本的资料共同建立。

Wiki 与当前 RAW 冲突时，记录当前 RAW 事实；Wiki 不覆盖它。翻译词表只决定叫法，不能证明实际材料或当前拥有量。未知 mod 先保留原文与确定 RAW 事实，不通过英文拼写强行套入原版定义。

七、查询语言与解析

7.1 输入归一化

保留原始输入和字符位置映射；另建搜索规范形。规范形执行 Unicode 规范化、ASCII 大小写折叠、全半角及搜索用简繁等价。名称显示字符串不被修改。

空格、连字符、引号和运算符在分词前保留，不能先删除全部空白。模型仍使用其自身 SentencePiece 规范化；不能将搜索用简繁／拼音串直接当作原模型 token 输入。

品质符号只有在原生字段确认其为品质包装时才脱离名称解析；自定义名称中的星号、数字、汉字和标点保留字面含义。squad.alias 及其他明确的自定义名称不参与翻译、词义改名或类别推断。

7.2 分词采用有义项的词图

以 Unicode 字符位置为节点，词典命中为边。完整英文短语、中文复合词、RAW 名称、材料名称、义项别名、数字和引用片段都可以形成边；保留相互竞争的完整切分，不只保留最长切分。

每条边带语法角色候选：对象、材料、属性、动作、用途对象、内容对象、专名、数量或连接词。未识别片段保持成一个未知词段，不为了凑匹配而拆成任意单字。

8 个解析槽位固定为：
  object / material / action / purpose / state / owner / quantity / literal_name。
字段再记录修饰范围和关系目标，支持嵌套 object，例如“装铁锭的木箱”。

7.3 形态规则

英语优先使用 RAW NAME 单复数对和词义词表中的不规则词形。-s/-es/-ies 仅在词典存在对应基本词且义项一致时合并。不能用普通字符串后缀判断一个英文原名的类型。

中文“子／儿”只在基本名词已被词典确认、词尾被该义项许可时作为可选口语形式。不能把“种子”削成“种”，也不能把“武器架”削成“武器”。“柜”与“橱柜”的关系由词义记录确认，不由共用最后一个字确认。

“木材／木制／wood／wooden”通过材料身份及 STATE_NAME／STATE_ADJ 对应；“牛皮／牛皮制”保留生物来源和材料种类。普通形容词不自动转化为材料。

中文复合词中心词使用已登记构词关系：武器架的中心是架，用途对象为武器；铁柜的中心是柜、材料为铁。词义目录允许“架类”等泛类别，但不能从任意中文词的末字自动建立硬继承关系。

7.4 默认查询含义

普通对象词在物品列表约束物品类型，在任务列表约束产物；裸材料词在材料列表约束材料，在物品列表约束物品基础材料，在任务列表保留“固定产物材料”和“可设置产物材料”的不同证明等级。

多个不同槽位默认 AND；显式“或／OR／|”形成 OR；“和／且／AND”连接条件。“不要／不含／不是／非”仅在后续可解析成完整字段或类别时引入否定，不对不死生物、无花果等完整名词内部拆分。引号中的内容始终为字面短语。

字段语法固定支持：
  类型:柜子 材料:铁
  产物:肥皂
  原料:兽脂
  用途:储存衣物
  状态:空
  名称:"原样名称"

普通中文是默认入口，字段语法用于精确消歧。无法形成完整语法的运算符片段回退为原始文本，不悄悄省略。

7.5 角色绑定

“铁柜”“铁制柜子”“柜子 铁制”统一为 object=CABINET AND base_material=IRON。
“装铁锭的木箱”统一为 object=BOX AND base_material=WOOD AND CONTAINS(item_type=BAR, material=IRON)。
“放衣服的柜子”统一为 object=CABINET AND STORES(clothing)，不要求柜子当前已装衣服。
“柜子里有衣服”要求 CONTAINS(clothing)，不只满足储物用途。
“制作柜子”要求 action=produce AND output=CABINET。
“用木头制作柜子”约束任务输入材料；只有任务的材料传递关系确认时，才进一步推出产物材料。
“武器架”是架这一对象；“武器”是武器类别；“存放武器的家具”才沿用途关系找到对应家具。

未知修饰词必须保留为待满足词段。“秘银柜子”即使认识柜子，也不能仅凭 CABINET 就返回所有柜子；当前材料目录没有秘银时，保留完整文本／不确定材料解释。

7.6 歧义管理

同一查询允许多个完整解释。每个解释保存来源、完整词段覆盖和逐槽位确定性，不再使用一个全局 certain。

上下文提高相关解释的排序，但不能用缺失信息制造确定类型。例如单位列表中的“铁锤”首先允许姓名和职业字段的文字匹配；只有物品搜索中的对象解释才应用物品类型约束。自定义名称精确命中始终保留独立的名称解释。

解析使用共享子结构和动态规划，合并等价状态，避免同义词、拼音和多音字组合成笛卡尔积。确定的词典路径不被向量候选的数量预算挤出；模型提出的弱解释可限定数量，并保留未穷尽标记。

八、召回与约束求值

8.1 确定召回

以下索引分别返回概念或候选身份，再取并集：
  原文／显示名完整及片段索引；
  词义别名索引；
  拼音全拼与首字母自动机；
  原生类型、定义、类别、材料的倒排索引；
  用途与任务输入输出的有向关系索引；
  有界拼写容错索引。

完整匹配、类别继承、已登记别名和完整拼音不使用全局 top-k 截断。命中一个概念后扩展其全部当前页面原生候选，不能只保留若干同名物品。

8.2 查询分支求值

每个解释生成一个 QueryPlan：
  domain + candidate_kind + target_role + positive_predicates
  + negative_predicates + lexical_residuals + allowed_relation_paths。

对象先确定，材料、状态、所有者、数量等限定在对应对象上求值。每个必须词段都要有正确字段中的支持；不能让同一无关标题片段同时证明材料、用途与产物。

一个候选在至少一个完整计划内满足全部条件才成为命中。不能从计划 A 取材料、计划 B 取类型，拼出不存在的解释。

只有直接、已确认、同字段的矛盾才能硬排除。模型近邻不具备排除资格。“物品含武器装饰”也不能用装饰字段证明其为武器。

8.3 原生英文命中统一进入计划

适配器向匹配器传 native_text_hit，不能提前 return 绕过解析。空查询返回原生空查询行为；普通未解析字面查询保留原生匹配；已明确的类型与限定条件仍需满足。

字段不可用时，匹配器返回保留原生行为所需的降级结果，但不把缺失字段的候选标为已经满足显式条件。计划执行失败不改变原生对象、开关或任务参数。

8.4 配方的三种材料含义

JobTemplate 的材料不是单一字符串，分别记录：
  固定产物材料；可选产物材料集合；投入物材料约束。

“铁柜”对固定铁柜任务是确定命中；对允许选铁、但尚未固定材料的通用柜子任务是可配置关联；对只有铁制工具参与、产物材料不是铁的任务不命中产物材料条件。

用约束蕴含与可满足性区分：
  固定参数或输出规则必然满足查询 → 确定。
  原生可选参数存在满足查询的配置 → 可配置关联。
  缺少输出关系，无法证明 → 未知。

可配置关联只表示这一任务入口能够进一步选到目标，不自动修改任务。现有页面无法表达该区别时，严格字段查询只返回确定命中；普通宽泛搜索可在相关结果层保留可配置入口。

8.5 数量与否定

数字必须带可确认的数量角色：库存数量、物品尺寸或任务批量。搜索框中输入“10 个柜子”不执行十次制作；只有页面支持对应数量字段时才执行该过滤。

显式排除某材料，要求材料字段已知且不属于被排除集合。Unknown 不被当成“不是铁”。普通名称中的负向词不引入这种逻辑。

九、拼音、容错与向量检索

9.1 拼音

中文义项先生成全拼与首字母，映射回同一个 sense_id。gz 保留所有符合当前领域的义项；不因为“柜子”最近使用就永久删除其他解释。完整拼音、首字母、英文原词分别保留通道标记。

多音字用已有逐字读音状态合并算法；词组词典中的已知读音优先排序，其他合法读音保留。拼音／汉字／英文混合输入按查询词图组合，不把任意拉丁串强制认作拼音。

9.2 容错

容错作用于已划定的词或名称字段，不跨越材料、内容、装饰和所有者边界。中心名词的关键末端不可随意删除。错误代价按字符编辑计算，短中文词默认不允许一字替换就跨类型命中。

沿用当前字符错误预算作为初始配置：中文至少三字、拉丁／拼音至少四字符才启用编辑距离；上限三次。新方案改变容错的作用域和约束顺序，不通过放宽所有阈值扩大结果。

同序省略只作用于已经确认的同一复合名称内部，不跨完整标题任意取两个同序汉字。完整专名的容错不生成物品类别事实。

9.3 向量的职责

向量库按对象义项、材料义项、动作义项和用途义项分别建立原型索引。一个义项的中文、英文和短释义保留多个向量；不把所有别名与长说明平均为一个向量。

查询向量只编码对应槽位的未知或弱识别词段。已确定的类型、否定、数字、关系词和精确专名由符号解析承担。整句向量可作为排序特征，但不能单独决定命中。

当前模型继续复用，不新增联网推理。初始概念召回半径沿用当前余弦距离 0.28；双字短词的直接候选通道沿用 0.22；单个未知汉字不进行通用 ANN 扩展。数值是引擎配置，不代表经本次实测得出的召回率。

召回后仍需逐槽位验证词义支持与对象字段相容性。当前 0.45 的中心词支持距离可作为弱语义支持的初始上限，但它不能把“武器架”的架解释成武器，也不能提升为已确认别名。

模型邻居必须满足：当前领域适用、关系路径获准、明确限定无冲突、全部必须词段得到支持。只相似于上下文而不支持中心对象的邻居丢弃。

9.4 近似预算

确定词汇与结构化关系先完整求值。ANN 预算只限制弱语义补充；预算耗尽记为 Pending／Approximate，不写成完全否定。

小型义项目录使用完整半径检索；大型目录以已有 VP 树分批访问，保存未访问分支。查询代次不变时继续补充。只有具备已绑定刷新回调的页面才自动发布补充结果；没有安全刷新入口的页面，在当前筛选调用内完成其选定检索级别，不能借模拟按键刷新。

模型不可用时，词义别名、类别、材料、用途、配方、拼音和容错均照常工作。未知识别能力下降，不将已知关联退化成纯英文搜索。

十、结果分层与排序

匹配器返回 MatchDecision：
  accepted / match_class / constraint_proof / relation_path
  / spelling_cost / semantic_distance / native_ordinal / completion_state。

固定分层如下，前层始终优先于后层：
  0 完整原名、显示名或明确自定义名称命中，且显式限定满足。
  1 同义义项、完整拼音或精确结构化对象命中，全部限定确定满足。
  2 类别包含及明确用途关系命中，全部限定确定满足。
  3 有界拼写容错命中，字段约束满足。
  4 可配置任务入口与弱语义关联，保留其证据等级。

层内按以下元组排序：
  必须词段覆盖 → 字段证明完整度 → 关系路径代价
  → 拼写错误代价 → 相似度 → 原生序号。

覆盖不完整的查询不通过总分补偿；例如材料条件缺失，不能因为“柜子”非常相似而过关。原生序号作为稳定末项，避免缓存构建顺序改变结果。

排序接入规则：
  已有安全排序路径的工坊结果，在原生分组内部稳定排序。
  其余仅有布尔过滤入口的页面保持原生顺序，使用相同命中语义。
  不重排具有类别层次、距离意义或原生依赖关系的数组。

名称显示仍使用当前翻译／自定义名称。若页面提供独立的搜索说明位置，仅显示“同义名称”“用于储存衣物”“可选择铁材”等直接影响选择的原因，不展示内部 concept ID、向量分数或技术标签。

十一、由“柜子”贯穿完整算法

输入“柜子”：
  词义目录识别 CABINET 的已确认俗称。
  库存页面以 INSTANCE_OF(CABINET) 召回全部当前候选橱柜。
  工单页面沿 PRODUCES(CABINET) 召回该分类提供的制作任务。
  定义本身的同义词识别不需要语义模型。

输入“木柜”“木制柜子”：
  CABINET 与 WOOD 分别进入对象与基础材料槽位。
  木制橱柜确定命中；只是装有木头的其他柜子不满足基础材料。
  模板任务是否命中，按其固定输出与可选材料分别处理。

输入“放衣服的家具”：
  查询目标为家具，关系为 STORES(clothing)。
  沿有条件用途关系寻找橱柜；不会把衣服本身当作结果。
  该关系不能推导任意场所、任意状态的实际储存行为。

输入“柜类”：
  进入独立的泛类别义项，按明确成员关系召回橱柜、书柜、展示柜。
  “衣柜”仍以 CABINET 精确义项为主，不因“柜类”存在而默认扩散到所有柜类。

输入“武器”：
  使用武器的类别／能力定义和当前页面对象角色。
  武器架只因用途与武器关联，不能在类型搜索中作为武器返回。
  输入“武器存放架”时，目标对象变成架、用途对象为武器，才命中武器架。

输入“箱子”：
  识别 BOX 类型的统一词义，并关联原生材料变名。
  原生 BIN、BAG、BARREL 仍是独立类型，不能因为现实中都能收纳而全部变成 BOX 同义词。
  “储物容器”使用独立用途类别，才允许根据条件覆盖多个容器类型。

上述内容定义新算法的查询语义，不是当前已观察到的游戏效果。

十二、其他页面的领域规则

12.1 物品、交易与建造材料
使用真实物品身份、基础材料、数量及原生允许集合。包含物的搜索遵循当前页面是否把容器与内容分别列为候选；命中内容不能悄悄改变交易勾选或以内容身份替代容器身份。

12.2 工坊与工单
默认对象词查询产物；显式“原料／消耗／用……制作”查询投入物；“需要的工具／容器”查询保留工具。生成乐器部件采用真实定义与 COMPONENT_OF 关系。RAW 反应、原生硬编码任务和生成任务都归入统一 JobDescriptor。

12.3 储物堆和工单条件
材料列只查询材料定义；类型列查询类型／子类型；属性列查询该属性的含义。页面类型传递到 QueryPlan，禁止把“空”当作具体物品名去做向量扩展。跨列综合查询需要适配器掌握完整条件结构；单列搜索不会替用户改其他列。

12.4 单位与小队
身份、姓名、别名、职业、物种、职责、状态分别建字段。搜索“铁匠”可匹配职业；“铁柜”作为明确自定义名字只按名称处理。squad.alias 原样显示，名称来源未知时也不凭拼写判定为自动名。

12.5 传说、日志、地点和组织
实体名和正文分开，正文关联只使用相应领域的角色与关系。不能将正文中的剑、柜子、王座等名词当成历史人物的物品类型。地点、组织和人物的同名记录保留独立实体 ID。

12.6 冒险对话与关键词
候选仍是原生提供的可选词／话题。关系检索只改变这些候选的搜索命中，不生成原生列表之外的新话题，不把语义关联当成已经发生的事件。

领域适配器共享解析、词义和匹配基础设施，但不共用一套无领域限定的对象排除规则。

十三、索引、缓存与线程设计

13.1 三层缓存

ConceptCatalog：原生类型、活动定义、材料、词汇、类别、用途和配方关系；不可变快照。
CandidateCatalog：某页面当前原生候选 ID 到 SearchDescriptor 的映射；只保存必要字段。
QueryPlanCache：规范查询、领域、目录代次和解析图；保存候选判定及完整性状态。

词向量按义项原型共享；实例只存概念 ID 和自身字段，不为每一件相同柜子重复建立完整语义树。生成专名保留轻量字面和拼音索引。

13.2 索引结构

别名词典用 Unicode trie／等价有限状态结构；拼音使用共享自动机；概念与材料成员使用倒排列表或位图；有向关系按起点、终点与角色建立索引；大量实例的动态字段只对已召回候选读取。

类别闭包在目录构造时生成。配方保留参数约束，不展开“每种材料 × 每种物品 × 每种译法”的所有标题组合。关系求值缓存以约束表达式为键，不能以屏幕标题为唯一键。

13.3 失效条件

缓存键包含：世界代次、实际 RAW／生成定义代次、翻译资源版本、词义关系版本、语言／拼音资源版本、模型身份、领域、页面所有者、候选集合代次和查询计划。

材料、内容、状态、品质、所有者等动态事实单独带状态版本。不能在字面标题未变时长期复用“空桶”等旧结论。界面重开或原生列表重建，原生地址相同也必须更新列表代次。

追加字符不保证语义结果单调变少；新查询重新解析，不能沿用前缀查询的失败集合。Unknown、Pending 和完整不命中分别缓存。

13.4 并发与生命周期

游戏指针和虚方法只在现有安全原生回调范围内访问；复制必要字段后形成不可变描述器。后台计算只消费快照，不跨线程解引用游戏对象。

目录更新采用新快照构造完成后切换；旧查询保留自己的目录引用，避免 ID 与词表版本交叉。跨世界时不复用旧实体 ID。卸载释放索引和查询状态，不保留指向旧核心的回调。

13.5 工作预算

优先完成字面、确定别名、结构化关系与完整拼音；弱语义随后处理。沿用现有工单目录分批准备的组织方式，将时间预算作为调度参数，不作为删掉确定结果的理由。

候选目录尚未建立时按需构造当前记录描述器，保证已知规则的第一次筛选语义与后续一致。完整相关结果需要原生安全刷新时使用现有绑定回调，不依赖人工切换页面、再次输入或模拟键鼠。

十四、数据格式与文件职责

保留现有 search-concepts.tsv 的兼容读取；将原有 group/kinds 转换成有作用域类别，将柜子这类同义词明确转入对应义项。新数据文件的职责确定为：

search-lexemes.tsv
  sense_id、surface、language、concept_id、domain、role、form_kind、source。
  只保存词义与叫法，不写显示译文替换规则。

search-relations.tsv
  subject、relation、object、domain、condition_id、version_scope、source。
  保存 RAW 未直接表达的游戏领域关系；不重复列出所有原生子类型。

search-predicates.toml
  声明条件表达式：字段比较、集合包含、AND／OR／NOT、模式与场所条件。
  表达式为受限数据语言，不执行任意脚本。

search-native-bindings.tsv
  将翻译命名空间和原生类型／子类型身份显式连接；明确哪些记录是名称文法、哪些是类型、哪些是领域类别。
  可从已存在的原生结构直接读取的定义不以手写清单复制。

上述四个文件已创建，并接入目录读取、现有资源版本刷新和正式部署入口；search-concepts.tsv 继续兼容读取。

来源元数据只用于解释词义和冲突裁决，不构建新的专项检查体系。数据更新通过已有资源版本刷新进入新目录；纯数据修改仍按项目规则原地使用，不触发编译或生成器。

十五、按依赖顺序实施的改动

第一步：统一身份和候选描述器。
  将 SearchItemTaxonomy 中的翻译命名空间类型与原生类型拆开；引入 DefinitionId 和活动 RAW 来源；现有物品、工坊、工单接入传递 CandidateKind、领域和可用原生字段。保留现有字面与拼音入口。

第二步：建立有义项词典与条件关系目录。
  接入完整 RAW ID、TOOL_USE、FURNITURE、材料定义和任务输入输出；将现有别名、类别与翻译词汇迁入有来源的义项记录。先完成确定数据，不用模型猜身份。

第三步：替换单一 qualifier/certain 查询结构。
  引入词图、QueryPlan、字段角色、限定词与逐槽位确定性；实现对象、材料、用途、输入输出和否定的组合。普通字面查询保留兼容解释。

第四步：统一匹配决策与缓存。
  PreparedSearchText 逐步只负责字面／拼音字段索引；对象约束放入共享 SearchMatcher。所有原生 substring 命中进入同一决策流程。缓存加入领域、候选代次和字段状态。

第五步：把现有模型接到义项与槽位。
  复用 search_semantic_model.h；减少逐候选完整标题 ANN；明确近似完成状态、弱关联等级和角色覆盖。已知类别、别名和用途不再依赖模型是否存在。

第六步：扩展其余领域适配器。
  储物堆、工单条件、建造材料先接明确的字段类型；单位、命名、传说、日志和对话接各自描述器。已有页面排序边界保持不变。

  src/search_normalization.inc：Unicode NFKC、搜索用简繁等价、原文字符范围映射；不改变显示名称。

  src/search_item_taxonomy.inc：仅保留词汇基础工具，不再以译名建立对象身份或扫描磁盘 RAW 宣布当前世界事实。
  src/pinyin_search.inc：保留拼音算法，替换查询及候选匹配协调层。
  src/search_similarity.inc：保留向量／编辑距离基础设施，按义项和字段检索。

  src/dfcn.cpp：统一各领域搜索入口，继续使用现有安全回调。
  tools/search_unicode_source.py：由现有正式构建入口生成 Unicode 表和固定 df-structures 原生枚举元数据。
  tools/build_history_layouts.py：为描述器生成所需结构字段与虚方法布局。

实现中的生命周期处理：词义与查询计划按资源、模型和世界快照代次更新；原生候选按所有者、列表代次和记录身份保存。动态描述器在原生调用中重新复制，匹配结论不跨调用复用，避免名称不变时沿用旧状态。模型原型按义项和槽位共享，当前筛选调用完成整个半径检索，不使用全局 top-k 截断或需要人工刷新的后台补充。

名称片段与字段边界：普通片段在类型相容的对象自身名称内匹配，不以中文名词词尾建立硬 IS_A 关系，不借任务投入物、工具或装饰标题证明产物。完整名称保留独立解释；普通片段同时服从已知字段冲突，明确字段、数量、角色和否定条件不被原生 substring 提前放行。名称、正文、材料、所有者、数量和状态分别求值，未知子类型保留未知，不因缺失子类型定义宣布全部事实已知。字段内的拼音和输入片段使用该字段自己的名称，不能借外层标题满足限定。引号保留字面含义，自定义名称及标点原样显示。

其余领域入口：单位和树种使用活动种族、阶层及植物定义；材料和属性选择器保留原生列类型；命名词库保留 WORD/POS 身份；图案、传说、日志与对话共用查询计划。传说描述与协议卡片的多个正文、人物和对象字段作为同一原生记录求值，允许完整组合条件跨字段命中。所有者姓名来自实际单位引用，并保留原文、昵称和现有姓名译法。译文词汇按命名空间和义项提供别名，不承担原生类型证明。

索引与性能处理：词典以完整名称索引连接活动定义与翻译，不逐词扫描全部定义；相同词面的拼音索引只构造一次，多音字按首字母缩小查询范围并保留全部读音，有限拼写与弱语义分阶段共享查询解析。词义模型按不同词面共享原型；已命中字面或拼音的完整分支及时返回，部分输入优先匹配字段名称。关系闭包按实际领域按需缓存，不预计算未使用的全目录闭包。原生物品标题捕获只保存相邻原生调用的参数，消费当前查询时才复制需要的状态；数量、品质、磨损、内容物、装饰、部件和所有者按查询字段读取，动态状态不复用旧匹配结论。

目录生命周期：静态世界目录在世界、查询或列表边界刷新，逐行调用短时复用快照；姓名与树种查询只准备身份目录，文本和属性查询不建立原生物品材料目录。任务事实按当前原生参数和目录代次复用，身份在每次调用绑定。历史人物等补充材料使用按世界和资源代次隔离的自有事实缓存，不逐行复制并替换整个世界目录。标题文法、查询计划、词面和弱关联结果按各自代次复用；纯文本缓存不继承其他候选的原生命中标记。材料查找和类别选择采用索引，筛选过程不建立未使用的全候选倒排表。

任务描述器分别保存固定参数、可选材料、投入、产出和保留工具；材料传递、材料反应产物、生成乐器部件与有条件防具分类来自活动定义和原生字段。可选材料集合与字段完整性分别记录，存在可选解不会替代严格字段查询需要的确定证明。

按照项目规范，未新增测试、专项检查脚本、样例、夹具或检查报告；代码全部实现后使用项目规定的同一编译部署入口。

十六、完成边界

方案保证的设计边界是：确定词汇与确定游戏关系形成可追溯的匹配；所有明确限定保留其角色；模型不能推翻事实；搜索始终落在原生候选集合内。

任意生造词、未声明的模组用途、无法读取的实例状态以及模型没有学到的同义词仍可能无法解析。对此保留未知状态和字面通道，不伪造对象事实。没有把本次离线反编译或算法定义表述成游戏内最终效果。
